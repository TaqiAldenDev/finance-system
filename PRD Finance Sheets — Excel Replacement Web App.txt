PRD: Finance Sheets — Excel Replacement Web App
Oct 10, 2026 · @ghost
1. Overview
Finance Sheets (working title) is a bilingual web app on Next.js and Supabase that replaces Microsoft Excel for daily finance work, adding a tamper-proof audit trail, role-based access, and a day-based access rule that Excel cannot enforce.

Core differentiators over Excel:
* Staff see and edit only the current day. Past days open only through a 1-hour, read-only session.
* Every operation (login, view, edit, delete, import, export, print) is logged and cannot be altered.
* Accounts are created only by the Super Admin; there is no public signup.
* Full English and Arabic interface, with correct right-to-left layout.
2. Problem, Goals and Success Metrics
Excel files cannot control who changes finance data, when, or prove what changed, so errors and fraud go undetected and files multiply.
Problems today
* No audit trail: nobody can prove who changed a number, or what it was before.
* No real permissions: anyone with the file can edit any day, including closed days.
* Version chaos: copies are emailed and edited in parallel.
* No structure enforcement: formats, categories, and totals depend on each user's discipline.
* Arabic and English mix poorly in one workbook, especially right-to-left layout.
Goals
1. Replace Excel for daily finance entry, with the same speed and familiarity (grid, formulas, import and export).
2. Make every action traceable to a named user, with old and new values.
3. Restrict staff to the current day, with a controlled 1-hour read-only window for past days.
4. Give admins faster review, approval, and reporting than Excel allows.
5. Deliver a first-class English and Arabic experience.
Non-goals (v1)
* Full accounting (general ledger, tax filing, payroll).
* Public signup or multi-company SaaS tenancy.
* Native mobile apps.
* Bank feed integration.

5. Key Workflows
Five workflows define the product: daily work, history access, day close, account provisioning, and audit review.
W1. Staff daily work
1. Staff signs in with the email and password the Super Admin created.
2. The app opens today's sheet, built from the active template with the previous day's closing balances.
3. Staff enters or pastes rows; formulas, validation, and totals update live.
4. Each edit is saved automatically and written to the audit log with old and new values.
5. At the end of the shift, staff submits the day for approval.
W2. Viewing a past day (1-hour read-only session)
1. Staff chooses "View previous day" and picks a date.
2. The app requires a short reason and records it.
3. The server creates a history session that expires 1 hour later.
4. The past day opens read-only with a visible countdown; edit, delete, import, and paste controls are disabled, and the database rejects any write attempt.
5. When the hour ends, access closes automatically and the user returns to today's sheet. A new session needs a new reason.
W3. Day close and approval
1. Staff submits the day. The sheet becomes read-only for staff.
2. An Admin reviews totals, flagged rows, and attachments.
3. The Admin approves (the day locks and balances carry forward) or returns it with a comment (staff can fix it again).
4. Only the Super Admin can reopen a locked day, and the reason is logged.
W4. Creating a user
1. Super Admin enters name, email, role, and language.
2. The system generates a temporary password and creates the account through the server-side admin API.
3. The user signs in and must set a new password before anything else.
4. The Super Admin can reset, disable, or change the role at any time; each change is logged.
W5. Audit review
1. Admin or Super Admin opens the audit viewer.
2. They filter by user, date range, action type, or sheet, and open any entry to see old and new values.
3. They can open the history of a single cell, and export the results.

	7. Non-Functional Requirements
Security and auditability come first; performance and usability must match what staff expect from Excel.
7.1 Security
ID
	Requirement
	NFR-SEC-01
	Row Level Security is enabled on every table. Access rules for role and date are enforced in the database, not in the UI.
	NFR-SEC-02
	The Supabase service-role key is used only on the server and never sent to the browser.
	NFR-SEC-03
	All traffic uses HTTPS (TLS 1.2 or higher); data is encrypted at rest.
	NFR-SEC-04
	Passwords are hashed by Supabase Auth; the app never stores or logs plain passwords.
	NFR-SEC-05
	Protection against OWASP Top 10 risks: injection, XSS, CSRF, broken access control, insecure direct object references.
	NFR-SEC-06
	Security headers (CSP, HSTS, X-Frame-Options) and rate limiting on login and write endpoints.
	NFR-SEC-07
	Uploaded files are scanned or restricted by type and size, and stored in private buckets.
	NFR-SEC-08
	Every role and date rule has automated tests that try to break it (for example, staff reading yesterday without a session, or editing during a session).
	NFR-SEC-09
	Secrets are kept in environment variables and never committed to the repository.

12. Open Questions and Acceptance Criteria

* ☐ Can staff delete rows today directly, or must deletions go through an Admin?
